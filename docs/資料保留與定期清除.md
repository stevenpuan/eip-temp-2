# 資料保留與定期清除（後台排程）

建立日：2026-08-29　　migration：`20260829155653_eip_purge_maintenance_scheduled_cleanup`

## 一句話

每天台北時間 **02:00** 自動跑一支 `eip_purge_maintenance()`，
依照兩張參數表把過期的日誌、通知與回收區資料真的刪掉，並留下執行紀錄。

## 排程

| 項目 | 值 |
|---|---|
| cron job | `eip-log-purge-daily`（jobid 2） |
| 排程 | `0 18 * * *` UTC ＝ 台北每日 02:00 |
| 指令 | `select public.eip_cron_guarded('eip_purge_maintenance')` |
| 失敗處理 | `eip_cron_guarded` 會寫 `error_logs`、記 `eip_notification_miss`，並通知所有管理者 |

改成半夜 02:00 是因為這支會真的刪資料，避開上班時間比較安全（原本是 23:00）。

## 保留天數在哪裡改

### 1. 日誌與成長表 → `eip_purge_policy`

| key | 對象 | 天數 | 說明 |
|---|---|---|---|
| `error_logs` | 錯誤紀錄 | 90 | |
| `activity_logs` | 操作紀錄 | 90 | |
| `audit_logs` | 稽核紀錄 | 90 | |
| `notification` | 站內通知 | 180 | 超過保留期一併清；那麼久的 LINE 待送也已無法送出 |
| `eip_notification_miss` | 通知失敗紀錄 | 90 | 純除錯用，沒有任何頁面在讀 |
| `eip_assistant` | AI 助理對話 | 180 | 依對話**最後一則訊息**時間算，整段對話一起清 |
| `line_bind_code` | LINE 綁定碼 | 7 | 已使用／已過期／太舊的 |

改法：`update eip_purge_policy set days = 365 where key = 'audit_logs';`
`is_active = false` 可以單獨停掉某一項。

**任務異動紀錄（task_change_log）與任務回報（task_update）沒有獨立規則**，
它們跟著任務走：任務被永久刪除時 cascade 一起走，任務還在就一直留著。

### 2. 回收區（軟刪除）→ `eip_deletion_policy.retention_days`

九個模組一律 **180 天**。這個欄位以前是 NULL 而且全庫沒有程式在讀，現在這支排程會讀了。

改法：`update eip_deletion_policy set retention_days = 365 where module_key = 'eip_tasks';`

**稽核軌跡保護照舊**：`purge_guard` 會先跑一次，擋下來的就不刪，只計入 `blocked`。

- 任務：有協作者、有變更紀錄、有進度回報、有他人完成的子項、有子任務 → 不刪
- 工作日誌：主管看過、已送出、有附件 → 不刪

也就是說時間到了不代表一定會消失，共同產出的東西會一直留在回收區。
2026-08-29 的模擬結果：174 筆已刪任務裡 **127 筆會被守衛擋下**、只有 47 筆可清。

## 怎麼看它有沒有在跑

```sql
select ran_at, dry_run, ok, duration_ms, detail
from eip_purge_run_log
order by id desc
limit 10;
```

`detail` 是 jsonb，每一項是刪掉的筆數；回收區是 `{"purged": n, "blocked": m}`。
某一段出錯不會中斷其他段，會在 `detail` 裡留 `"ERROR: ..."`。

## 先試跑不刪

```sql
select jsonb_pretty(public.eip_purge_maintenance(true));   -- p_dry_run = true
```

只統計、不刪任何東西，一樣會寫一筆 `eip_purge_run_log`（`dry_run = true`）。

## 權限

- 函式是 `security definer`。cron 呼叫時 `auth.uid()` 是 null，直接放行。
- 從前台呼叫則必須是 `company_admin`，否則丟「權限不足」。
- `eip_purge_policy` / `eip_purge_run_log` 兩張表的 RLS 都只開給 `company_admin` 讀，
  `eip_purge_policy` 另外開 update。

## 每次執行的批次上限

`p_max_per_table` 預設 500，指的是**回收區每個模組每次最多清幾筆**，
避免一次刪太多把交易拉長。累積的舊資料會分幾天清完，這是刻意的。
