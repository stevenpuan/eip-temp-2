# 「看起來能設定、其實沒作用」清理（2026-08-30）

這一類比功能缺一塊更危險：使用者勾了、按了儲存、看到「已儲存」，
就會相信那件事已經設定好了 —— 直到某天發現根本沒生效。

六項逐一處理如下。

---

## 1. 角色權限頁的「子頁面權限」分頁 → 入口收掉（程式碼保留）

**查證**：後端所有 RLS 政策與 `eip_has_perm()` **只讀 `role_module_permissions`**，
全庫沒有任何一處讀 `role_page_permissions`，該表至今 **0 列**。
也就是說那個分頁勾什麼都不會生效，但畫面上看起來像真的鎖住了某些頁面。

**作法**：`role-permissions.tsx` 加 `SHOW_PAGE_PERMISSIONS = false`，
關掉分頁列與該分頁內容。`savePage()`、`pVal()`、`pCycle()` 等程式碼**全部保留**，
哪天後端真的實作兩層權限，把旗標改成 `true` 就回來了。
只剩單一分頁時連 TabsList 一起隱藏，畫面上不會出現只有一個頁籤的怪樣子。

副標題也一併改成「以模組為單位設定各角色的檢視／新增／編輯／刪除／匯出權限」，
不再宣稱有兩層。

## 2. 代碼字典 lookups → 修掉真 bug ＋ 標示哪些是裝飾用

**真 bug**：開發歷程頁讀 `changelog_type` 時**沒有過濾 `is_active`**，
在代碼字典把某個選項「停用」，它照樣出現在下拉選單裡（設了等於沒設）。已補上過濾。

**裝飾用的部分**：`issue_severity` 與 `feature_request_status` 的選項其實**寫死在畫面程式裡**
（`issue-reports.tsx` 的 `SEVERITY`、`feature-requests.$id.tsx` 的 `STATUS_LABEL`），
在代碼字典改不會有任何效果。**沒有刪掉資料**（刪了反而更難查），
改成在每個類別標題下標註用途，沒有人在用的那兩個用紅字標「改這裡不會生效」。

**順手修**：這一頁的新增／編輯／刪除三個寫入**都沒有驗影響列數**
（先前 49 處「假成功」的清理漏掉了這一頁）。RLS 擋下時 PostgREST 回 0 列而不是錯誤，
畫面照樣跳「已刪除」。三處都補上了。

## 3. 角色權限頁對 admin 的宣告與後端不一致 → 改後端

**問題**：畫面寫死「管理員擁有全部權限，無法調整」並鎖住勾選格；
前端 `can()` 也是 `if (isAdmin) return true`。
但後端 `eip_has_perm()` **只查資料表、完全不特判 admin**。

實查：系統設計師在 `role_module_permissions` 裡有 **10 個模組不是全開**，
例如 `org` 的 create/edit/delete 全是 false、`eip_calendar` 只有 view。
只要哪天有 RLS 走到 `eip_has_perm('org','edit')`，系統設計師就會被自己的系統擋住，
而且因為畫面把勾選格鎖住了，**在 UI 上永遠修不回來**。

**作法**：migration `eip_has_perm_admin_matches_frontend` —— 後端補上
`public.is_admin(auth.uid()) or ...`。這不是放寬權限，是把已經對使用者宣告過的行為補實作。

**驗證**：系統設計師 `org:edit` false→true；
管理者的 `org:delete`／`users:delete`／`audit_logs:edit`／`system_config:edit` **全部維持 false**、
`org:edit` 維持 true；一般成員 `users:edit` 維持 false、仍只看得到 1 份文件。
非 admin 角色完全沒有被連帶放寬。

## 4. 通知設定可以存成「空收件範圍」→ 擋下來

**問題**：把某個事件的收件範圍全部取消、通知卻還開著，儲存會成功，
但那個事件從此**不會通知任何人**，而且畫面上完全看不出來。

**作法**：`notification-settings.tsx` 儲存前檢查 ——
事件還啟用、站內或 LINE 還開著、但收件範圍是空的 → 紅字擋下並點名是哪幾個事件。

**三個事件豁免**（`SCOPELESS_BY_DESIGN`）：`announcement_published`、`direct_notify`、
`meeting_invited`。它們的收件人是呼叫端當場指定的（公告＝發布對象、會議＝與會者），
`recipient_scopes` 本來就是空的，**是正常設計不是漏設**。

**順手修**：`save()` 的 update 也沒驗影響列數，一併補上。

## 5. `eip_notification_miss` 沒有任何頁面在讀 → 不動，說明原因

249 筆。這是診斷表，不是「假設定」—— 沒有畫面宣稱它有作用。

**而且排程失敗不會被漏掉**：`eip_cron_guarded` 失敗時除了寫這張表，
同時會寫 `error_logs` 並**推播通知給所有管理者**，所以真正要緊的事情看得到。
新的定期清除程式也會清 90 天以上的資料，不會無限長大。

要做觀測面板是新功能，不在這次範圍。維持現狀。

## 6. `manual-assets` 儲存桶零政策零引用 → 不動，說明原因

2026-08-17 建立，**0 個檔案、0 條政策、非公開**。
沒有政策代表除了 service_role 以外**任何人都存取不到**，所以它不是資安破口，
只是佔著一個名字。

**沒有刪除**：刪除正式環境的儲存桶是不可逆操作，而留著的成本是零。
要清乾淨的話請自己在 Supabase Dashboard → Storage 刪掉即可。
