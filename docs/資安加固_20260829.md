## 7. 線上手冊未消毒就渲染（儲存型 XSS）

**問題**：`DocRenderer.tsx` 在 HTML 模式下直接 `dangerouslySetInnerHTML={{ __html: content }}`。
原本的理由是「只有有編輯權的人寫得進 `doc_pages`，算可信內容」——
但那是 4 個帳號（系統設計師＋3 位管理者）。其中任何一個被盜或一時貼錯東西，
惡意腳本就會在**全體員工（含系統設計師本人）已登入的瀏覽器**裡執行。

**原本卡住的地方**：`sanitize-html.ts` 的白名單不含 `<style>`，而手冊自帶一段
6.9 KB 的 `.eip-manual` scoped 樣式。直接套消毒會把 `<style>` 展開成一大段可見文字，
整份手冊的排版就毀了。

**作法**：擴充消毒器而不是繞過它。
- 白名單補上手冊實際用到的標籤：`style` / `figure` / `figcaption` / `section` / `nav`
- 全域屬性補上 `id`（目錄的 49 個錨點要用）、`title` / `lang` / `dir`
- `<img>` 補上 `loading` / `decoding`
- 新增 `DROP_TAGS`：`script`／`iframe`／`form`／`svg`／`meta` 等**整棵砍掉**，
  而不是像以前「展開保留文字」（否則 `<script>alert(1)</script>` 會在畫面上留下 `alert(1)` 這行字）
- `<style>` 保留但內容過濾（`sanitizeCss`）：拿掉 `@import`、`expression()`、
  `behavior`、`-moz-binding`、`javascript:`，`url()` 只留 `data:image`
  （擋掉用 CSS 屬性選擇器 + 外連 url 把內容外傳的手法）

**驗證**（在正式站的瀏覽器裡對真實手冊內容實跑）：

| 指標 | 消毒前 → 後 |
|---|---|
| 元素數 | 1156 → **1156** |
| 標籤種類增減 | **無變化** |
| 目錄錨點 id | 49 → **49** |
| `<style>` CSS 位元組 | 6914 → **6914** |
| 純文字長度 | 21011 → **21011** |
| 屬性數 | 716 → 765（+49＝49 個 `<a>` 補上 `rel="noreferrer noopener"`）|

攻擊向量實測：`<script>`／`onerror`／`javascript:` 連結／`iframe`／`svg onload`／
`form`＋密碼欄／`meta refresh`／`@import`／`url()` 外連／`expression()` **全數被清除**，
正常的 `<section id>`＋`<img src="/manual/…" loading="lazy">` 完整保留。

## 8. `eip_set_user_roles` 提權

**問題**：只驗 `users:edit`，不看被授予的是什麼角色。管理者（3 位）有 `users:edit`
→ 可以把自己或任何人設成「系統設計師」。

**作法**：加兩道
1. 非系統設計師不得**授予或移除**「系統設計師」（只有這一階受限，其他角色照舊）
2. 不得移除最後一位系統設計師（否則沒人能改回來）

**驗證**（RLS 模擬，交易全部回滾）：
- 管理者升別人為 admin → 擋下 ✅
- 管理者自升 admin → 擋下 ✅
- 管理者調一般角色 → 仍然可以，未被誤擋 ✅
- 系統設計師移除自己（目前只有一位）→ 擋下 ✅

## 9. `doc_pages` 全員可讀

**問題**：SELECT 的 qual 是 `true`，系統文件與 4 份 `*_bak_*` 備份對全體員工可讀。
前端有 `RequirePerm` 擋，後端完全不擋 —— 直接打 API 就拿得到。

另外 `doc_write` 是 `FOR ALL`，而 `FOR ALL` 也涵蓋 SELECT，
所以 3 位管理者（`eip_derive_app_role` 把 manager 映射成 `company_admin`）
還是能繞過新的讀取政策。

**作法**：
- SELECT 改成 `eip_has_perm(key,'view') or is_admin(auth.uid())` —— 跟前端同一把尺
- `doc_write` 拆成 `doc_insert` / `doc_update` / `doc_delete`，寫入權限完全不變，
  只是不再附帶讀取權

**驗證**（RLS 模擬）：一般成員仍看得到使用手冊、看不到系統文件與備份；
管理者仍看得到系統文件與手冊、**看不到備份**、編輯權未受影響；系統設計師看得到全部 6 份。
因為前端本來就這樣擋，**沒有任何人的畫面會改變**。

## 10. 稽核紀錄可偽造

**問題**：三張 log 表的 INSERT `with_check` 是
`user_id = auth.uid() OR user_id IS NULL` —— 任何登入者都能寫出「查不到是誰做的」紀錄，
也能塞假紀錄洗掉真的軌跡。

**作法**：收成 `user_id = auth.uid()`。
四支會寫 log 的函式（`eip_audit`／`eip_cron_guarded`／`eip_admin_reset_password`／
`eip_admin_delete_user`）都是 postgres 所有的 SECURITY DEFINER、有 BYPASSRLS，不受影響。
前端 `logging.ts` 改成沒有身分就不寫（原本會送 `user_id: null`）。

**驗證**：成員寫 `user_id=null` → 擋下 ✅；冒用他人 id → 擋下 ✅；寫自己的 → 正常 ✅

## 11. 從 LINE 建任務繞過角色檢查

**問題**：`line-webhook` 用 service_role，RLS 不生效。網頁端建任務要過
`task_insert` 政策（限 `company_admin`／`dept_manager`／`member`），
但 LINE 這條路只驗「有沒有綁定 LINE」→「唯讀」角色從網頁被擋、從 LINE 卻建得成。

**作法**：把同一條規則寫進 `insertTask()`，並在 `create_task` 暫存前先擋，
使用者才不會被問「要建立嗎」、按了確認才發現沒權限。

**目前影響 0 人**（唯讀角色 0 人、`app_user.role` 只有 company_admin 4／dept_manager 9／member 16），
純粹是把兩條路徑的規則對齊，避免日後開了唯讀角色才發現漏洞。
